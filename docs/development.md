# Руководство разработчика

## Процесс

1. Задача описывается в issue: контекст, цель, критерии готовности.
2. Работа ведётся в отдельной ветке: `feature/…`, `fix/…`, `docs/…`, `infra/…`.
3. Коммиты небольшие, по одному логическому изменению; сообщение объясняет, что изменилось.
4. Изменения попадают в `main` только через Pull Request. В описании PR — что сделано,
   зачем и какими командами проверено; PR ссылается на issue (`Closes #N`).
5. Рецензент запускает проект по README, смотрит тесты и документацию.

## Перед Pull Request

```bash
make check      # стиль, типы, тесты
make coverage   # покрытие
make docs       # документация собирается без предупреждений
```

Если менялась работа с базой или Docker:

```bash
make test-integration
make up && make down
```

## Зависимости

Прямые зависимости добавляются в `*.in`, после чего `make lock` пересобирает
`*.lock`. Lock-файлы коммитятся вместе с `*.in`.

## Документация

Исходники — в `docs/` (Markdown через MyST), диаграммы — Mermaid-файлы в
`docs/diagrams/`. Сгенерированный `docs/_build/` в git не попадает и вручную не
правится: изменения вносятся в исходники или в docstring-и кода.
